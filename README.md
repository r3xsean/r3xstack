# r3xstack

My personal agent skills, the ones I use every day.

Most of them pair your agent with a second model. They argue out a question, take a code change from request to wherever it should land, review and try to break a code change, have a fresh model read work that already exists and say how it would make it better, find what's worth improving in a codebase and see each improvement through, turn something you found (a post, a video, an article) into a decision about your workflow, decide which model and effort each role in your workflow runs on, and run UI design work with a council of models. The rest support that work: settling the decisions about a request that only you can make, building the checks that prove a change works, watching a video for what it says and shows, writing skills, AGENTS.md files and prompts, and keeping the default model for each role in one table. Where direction, taste or shipping is at stake, the skills stop for your decision.

**Requires [T3 Code](https://github.com/pingdotgg/t3code).** Several skills hand work to models from other providers through T3 Code's delegation tools, so they don't run in plain Claude Code or Codex. They take each model as the newest of its family that T3 Code offers, and start the agents on it through T3 Code:

- `back-and-forth` and `code-loop` start the other model as a T3 Code delegated task, and `see-it-through`, `incorporate` and `model-audit` reach it through them. `back-and-forth` keeps a debate in one continuing thread with T3 Code's thread messages, so the other model sees the whole argument, and a runner, when one is named, starts as a delegated task too.
- `second-look` starts its fresh reader on the model you name or its default. `see-it-through` also starts a runner and (through `second-look`) a second look on models of their own, a fresh fact-checker on a default model of its own to check public text, and, when a code loop ends with unresolved disputes, a fresh agent on the second look's model to read them. `incorporate` also starts a second look through `second-look`, and `kaizen` does on a close call.
- `design-process` starts its council members as delegated tasks.
- `kaizen` starts every agent it uses (its reviewers, merge agents, probes and debates) as a delegated task rather than a native subagent, since native subagents stop at 20; it launches each improvement as its own T3 Code thread, passes ship messages and your approvals between threads with thread messages, and checks on the threads it launched through T3 Code's thread list.
- `incorporate` also reads X links in a T3 Code browser tab, and `model-audit`'s meter reads Claude plan-limit readings from T3 Code's provider logs.

## The skills

| Skill | What it does for you | How to start it |
|---|---|---|
| [`see-it-through`](skills/see-it-through/) | Takes a code change from your request to its destination (a tested local change, a pushed branch, an open PR, merged or deployed), with another model reviewing. Normally you approve the approach before it builds and the result before it ships, and answer whatever its grill asks you first. With auto approve, the result is the only thing you approve. | "see it through" plus the change; add "with `<family>` at `<effort>`" to choose the other model, and "auto approve" to approve only the result |
| [`kaizen`](skills/kaizen/) | Finds what's worth improving in a codebase: reviewers read it through a set of lenses, and by default each finding is sized and argued worth doing or not; when you say "go" each one to do runs as its own `see-it-through`, with its ship message coming to you. | "kaizen", optionally with what to cover ("kaizen the sync code, just performance, chat only"); "kaizen continue" picks a pass back up |
| [`code-loop`](skills/code-loop/) | Has another model review a code change and try to break it with tests, over up to three rounds (plus one reproduction round for a blocker or should still disputed after them), and fixes or disputes what they find. | "code loop with `<family>` at `<effort>`"; other skills also start it |
| [`back-and-forth`](skills/back-and-forth/) | Answers a question by having your agent (or a runner in its place, when one is named) and another model each answer it without seeing the other's answer, then argue it out and check the facts the answer rests on. | "go back and forth with `<family>` at `<effort>`" plus the question |
| [`second-look`](skills/second-look/) | Has a fresh agent, on a model you name or its default, read work that already exists (a proposal, a plan, a back-and-forth's record, a diff), unbound by it, and say how it would make it better; then settles each point it raises as adopted, conceded or held. | "get a second look at" plus the work; add "with `<family>` at `<effort>`" to choose its model; `see-it-through`, `incorporate` and `kaizen` also start it |
| [`grill-me`](skills/grill-me/) | Settles with you the decisions about a request, plan or idea that only you can make, and nothing else: it finds facts itself and asks only what would change what you get, in numbered rounds, each question with a recommended answer that a plain "yes" accepts, and states the rest as assumptions you can object to. | "grill me" plus the request, plan or idea; `see-it-through` and `writing-steering-files` also start it |
| [`make-verifiable`](skills/make-verifiable/) | Builds, extends or repairs a repo's verify skill: the check commands and scripted flows that prove a change works, with evidence. | "make this repo verifiable"; other skills also start it |
| [`design-process`](skills/design-process/) | Runs UI design work where you set direction and taste: blind design directions, refinement driven by your reactions, and a scored council of models comparing your screens with competitor apps. | ask to design, redesign or polish a UI, to run a design council on screenshots, or to record your reactions to a design |
| [`incorporate`](skills/incorporate/) | Turns a post, video or article you found into a decision about your skills and rules: change them, or record why not. Another model argues it out with your agent and, when its model is available, a second look reads their conclusion. | "incorporate this into my workflow" plus the source; add "with `<family>` at `<effort>`" to choose the other model |
| [`watch-video`](skills/watch-video/) | Watches a video from a link (YouTube, X or any site yt-dlp handles) or a local file: gets its transcript and details, looks through frames from the whole video, and answers from what it says and shows, tying each point to a transcript time or a frame it viewed. | share a video and ask what it says or shows, or for its transcript; `incorporate` also starts it |
| [`model-audit`](skills/model-audit/) | Decides which model and effort each role in your workflow, or in one automation, should run on, from what your plans actually charge and what the evidence shows, and changes only what those roles touch. | "audit the models with `<family>` at `<effort>`", naming the workflow or the model that launched; `incorporate` also starts it |
| [`writing-steering-files`](skills/writing-steering-files/) | Writes or edits a skill, an AGENTS.md/CLAUDE.md, an automation prompt or a product system prompt with you, agreeing the intent and structure before any text exists. | ask to write or change one of those files; `incorporate` and `model-audit` also start it |
| [`model-defaults`](skills/model-defaults/) | Holds, in one table, the model and effort each role runs on when you name none: the other model, the runner, the breaker and fact-check, and the second look, with a column for light and medium runs and one for heavy runs. It does no work of its own. | nothing to say: `see-it-through`, `second-look`, `incorporate` and `kaizen` read it; it's set so agents never load it unasked, and you can open it by typing its name |

## How they fit together

The skills build in layers. `grill-me`, `back-and-forth`, `second-look`, `code-loop` and `make-verifiable` each do one job, and you can start any of them on its own. `see-it-through` strings them together to take one change from request to destination, and `kaizen` sits on top of that, launching a `see-it-through` run for each improvement it judges worth doing. `incorporate`, `model-audit` and `writing-steering-files` look after the workflow itself: what goes into your skills and rules, which model each role runs on, and how the files get written. `design-process` and `watch-video` stand on their own, though `design-process` reviews code with `code-loop` and `incorporate` reads videos through `watch-video`. `model-defaults` holds the models the others fall back on. In detail:

- **`see-it-through`** is the end-to-end flow. Unless the change is already built, it runs **`grill-me`** once it has grounded the change in the code and before it weighs whether the change is worth its cost, and your answers become part of the request, with the assumptions the grill stated going along, marked as the agent's. With auto approve, the agent answers the grill itself with each recommended answer. In a medium or heavy run (the tiers are under **Light, medium or heavy** in its section below) it settles the approach with **`back-and-forth`**, argued by a runner on your agent's behalf; in a light run it does so only when its design triggers fire or the strong approaches differ materially; for a change that's already built, it runs none. When a back-and-forth runs, a second look through **`second-look`** reads its record (unless the second look's model is unavailable), and what that raises goes back into the same back-and-forth. Before the explainer (or, for a change that's already built, in its write-up of the approach as built), it goes through the acceptance conditions in `code-loop`'s brief, plus who relied on the behaviour it's changing, and names the test that will cover each one that applies, or the limitation it accepts. It reviews the finished diff with **`code-loop`**, and once you've approved the ship message, a fix for a review comment that changes behaviour gets its own code loop. When the repo has no verify skill, or the skill doesn't cover the flow it needs, building that coverage with **`make-verifiable`** becomes part of the approach. When a user can see or do what changed and the verify flow can't capture it, it extends the flow with `make-verifiable`, and when the change alters a flow the verify skill covers, it updates that flow in the same change.
- **`kaizen`** sits on top of `see-it-through`. It changes no code itself: every improvement it judges worth doing is launched as a `see-it-through` run in its own thread, with auto approve unless it's a direction item or you said "`<item>`: grill me" for it, so an auto-approved run's ship message is where you approve. When the repo has no verify skill, it first launches one `make-verifiable` run for the flows the launched items touch, and launches the rest once that has landed. Unless you turn debates off, its worth-it debates are `back-and-forth` runs argued by a runner, on the light-and-medium runner and other-model defaults in **`model-defaults`** unless you name others, and a close call that doesn't turn on one unmeasured number gets a `second-look`. It reads the repo's verify skill and lessons log, when the repo has them, before it audits.
- **`code-loop`** runs the repo's checks through its verify skill when the repo has one. In round 1 of a light run from `see-it-through`, it starts the test-writing breaker only after the reviewer replies, and only for what the reviewer couldn't verify that a test could settle. In any run, a later round starts a breaker when a fix changed behaviour, ordering or ownership.
- **`make-verifiable`** builds the verify skill that `see-it-through` and `code-loop` lean on. Its recording helpers are built to make clips that meet `see-it-through`'s capture rules.
- **`incorporate`** takes its default other model from `model-defaults`, from the light-and-medium column, since it has no tiers. When the source is a video, it reads it through **`watch-video`**. It argues what to change with **`back-and-forth`**, then gets a second look at the debate's conclusion with `second-look`. When there's a change, or its second look holds a point, it hands the drafting to **`writing-steering-files`**. Adopted scripts are checked with `code-loop`, and repo verification goes through `make-verifiable`. When the source announces a model you could run, it hands the whole run to **`model-audit`** instead.
- **`second-look`** sends what it raises back to whoever produced the work: into the same back-and-forth when one did, which is how `see-it-through`, `incorporate` and `kaizen` use it. Its default model is the second look's default in `model-defaults`.
- **`model-defaults`** is the one place the defaults live. `see-it-through` takes each role's default from it for the run's tier; `second-look`, `incorporate` and `kaizen`, which have no tiers, take the light-and-medium column. Change a default there and every skill that reads it follows. Install it with the others: those skills link to it as a sibling folder.
- **`model-audit`** argues the recipe you picked with `back-and-forth`, reruns `code-loop`'s regression suite when the reviewer's or breaker's model or effort changes, and makes each change by its file's route: steering files through `writing-steering-files`, code and configuration through `see-it-through` in the repo that holds them.
- **`design-process`** puts new harness code through one `code-loop` round before designers use it. During refine, it reviews a structural change with `code-loop` when the change touches code beyond styling and you've named a model.
- **`writing-steering-files`** puts the decisions about a file that only you can make through **`grill-me`**. It runs a skill's regression suite, such as `code-loop`'s, before and after an edit to that skill, when the edit touches what the suite exists to test and you've approved the run. Any observed failure the edit answers is added as a case first.

## Naming the other model

`back-and-forth`, `code-loop` and `model-audit` each need a model family, such as `sol` or `opus`, and a reasoning effort. They use the newest model of that family that T3 Code offers. In `back-and-forth` and `code-loop`, a provider alone, such as `gpt` or `claude`, isn't a family. If you leave out the family or the effort, the skill asks and does nothing else until you answer. When another skill starts `code-loop`, `back-and-forth` or `model-audit`, that skill passes the model, and it can give `code-loop`'s breaker a separate one. In `model-audit`, the model you name argues the chosen recipe with your agent; it isn't a candidate for any role.

`see-it-through` and `incorporate` take a family and an effort the same way, but have defaults, all kept in [`model-defaults`](skills/model-defaults/). Name neither and `see-it-through`'s other model is the newest Sol model at high in a light or medium run, and the newest Astra model at high in a heavy one (the tiers are under **Light, medium or heavy** in [its section](#see-it-through)); `incorporate` has no tiers, so it uses the light-and-medium default, Sol at high. A model you name is used in every tier. Name only one of the two and the skill asks for the other before doing anything else. In `see-it-through`, the other model argues every back-and-forth and reviews every code loop in the run, while the code loop's breaker and the fact-check of public text run on a default of their own, the newest Sol model at high; in `incorporate`, it runs the back-and-forth, or the `model-audit` it hands a model launch to.

Two more roles have defaults of their own, and in `see-it-through` you can name a model for either. In `see-it-through`, your agent doesn't argue the approach itself: a **runner** does, a separate agent that argues your side through `back-and-forth` against the other model; by default it's the newest Opus model at xhigh, or the newest Fable model at high in a heavy run. When the runner's model isn't available, your agent says so and argues the approach itself with the other model. Outside `see-it-through`, `back-and-forth` uses a runner only when you or the calling skill names one. A **second look**, a fresh agent that reads what the debate concluded, runs through `second-look` in `see-it-through` whenever a back-and-forth does, and in `incorporate` unless the run is handed to `model-audit`; by default it's the newest Fable model at high, in every tier. When its model isn't available, the skill says so (`see-it-through` in the explainer, `incorporate` in its message to you after the debate) and goes on without one. Started on its own, `second-look` takes a family and an effort the same way: name neither and it uses that Fable default, name only one and it asks for the other before doing anything else, and when the model isn't available it says so in its report and goes on without a second look. `see-it-through` also uses the second look's model for a fresh agent that reads any disputes the code loop left unresolved, before the ship message.

`kaizen` doesn't ask for a model. Its reviewers, and the `see-it-through` runs it launches, run on your agent's model and effort; its probes on the newest Sol model at high; its debates on the light-and-medium runner and other-model defaults in `model-defaults`; and the second look on a close call on the second look's default there. Name a model and effort for any of those roles when you start it, and it uses that instead.

`design-process` asks only for the models a run needs. When a run will reach the council, it asks at the start who sits on it, with each member's model and effort, unless you already named them. When the capture harness needs new code, it asks which model reviews that code. Its explore designers run on a model you name, or on your agent's.

`grill-me`, `make-verifiable`, `watch-video` and `model-defaults` don't use another model, and `writing-steering-files` doesn't ask for one: its probes run on fresh subagents, except a skill's regression suite, which runs as that suite's README says.

## What they read and write

So you know what lands where before you install:

- `see-it-through` logs lessons, when a run has one, in the changed repo's `.agents/lessons/log.md`. When a change's design sets a boundary later changes must respect, the reason for a non-obvious ownership decision goes in the repo's AGENTS.md.
- `see-it-through` saves acceptance checks that won't be committed, and the runner's record of the debate, outside the repo; `code-loop` saves the breaker's kept tests as a patch outside the repo too.
- `kaizen` keeps its record of passes outside the repo, in `~/.agents/kaizen/<owner>-<repo>/`, or in the folder that holds your process for that repo when you keep one: one file per finding, kept across passes, a `STATUS.md` board and run log, a `runs/` folder per pass with its reviewer reports, baselines, debate records and scratch scripts, and a `report.html` and an `index.md` its script builds from them. The report page loads Mermaid from jsDelivr when you open it, to draw diagrams. A pass reads the code from a detached worktree, in the temp folder, of the remote default branch of the repo the work lands in (upstream's, for a fork), removed once every item is judged. A probe that runs the repo's own commands does so in a scratch worktree it removes when done, and each run it launches works in a new worktree from the remote default branch, with full access. A pass scoped to "this branch" reads that branch's head instead, and its runs start from that branch.
- `code-loop`'s regression suite builds its checkouts in a temporary folder unless you give it another, fetches a case's commits into that case's repo when they're missing there, and appends each run's results to `evals/results.jsonl` inside the installed skill; your cases go in `evals/cases/` there.
- `make-verifiable` puts the verify skill in the repo's `.agents/skills/verify/`, with its helpers in that folder's `scripts/`, and adds `.claude/skills` as a symlink to `../.agents/skills` when the repo has no `.claude/skills`. Its evidence goes to a git-ignored path.
- `design-process` keeps its files in `docs/design/`, and copies the captures of screens you approve to `docs/design/references/`. Other captures and its findings ledgers go in the git-ignored folder its `harness.md` names, and council packs go outside the repo. When a run builds prototypes, they live in their own entry or route that the production build never includes, with a check that enforces it.
- `incorporate` treats `~/.agents/skills` and `~/.agents/AGENTS.md` as your workflow, and logs each run in `~/.agents/sources/log.md`, except a run it hands to `model-audit`, whose log entry stands for it.
- `model-audit` logs an audit of your own workflow in `~/.agents/models/log.md`, and an audit of an automation in that automation's repo, where it already keeps decisions or else in a `MODELS.md` beside the workflow, with nothing personal in it. Its two scripts only read: `inventory.py` reads the workflow's folder and this machine's Claude Code and Codex session records (`~/.claude/projects`, `~/.codex/sessions`), and `meter.py` reads those records and T3 Code's provider logs (`~/.t3/userdata/logs/provider`). Raw records stay out of the log and out of the skill's folder.
- `second-look`'s fresh agent changes no file but scratch files of its own.
- `watch-video` keeps each run (the downloaded video, the transcript, the contact sheets and the frames it pulls) in a new folder under `watch-video/` in your temp folder, and deletes runs 3 days after their last use; `-o <file>` also writes the transcript where you say. The first time a video needs transcribing locally, unless faster-whisper is already installed for the Python that runs the script, it creates a Python environment of its own in `~/.cache/transcribe-youtube` and installs faster-whisper there. It uses no API key.
- `writing-steering-files` keeps copies of the files it edits outside their folder while a run lasts, to diff each round against, and deletes them when the run ends.

For a repo you don't own, the lessons log and the verify skill go in the folder that holds your process for that repo, never in the upstream repo's files, and `see-it-through` takes on only the structural correction the approved change needs: wider cleanup, a changed approach and refactors raised by the lessons log become proposals to the maintainer. Where a repo has its own rules, the skills defer to them: `see-it-through` follows the rules of the repo it changes and any process file you point it to, `code-loop`'s reviewer checks the change against the repo's rule files (such as AGENTS.md or CONTRIBUTING.md), `make-verifiable` puts the verify skill where the repo's AGENTS.md says when it names another place, `kaizen` reads upstream's rules for contributions and follows them in how each item lands, and `design-process` follows the project's AGENTS.md on dependencies, dev servers and what gets committed, asks you before doing anything those rules forbid or reserve for discussion, and uses another place for its files when that AGENTS.md names one.

## Install

```bash
git clone https://github.com/r3xsean/r3xstack.git
mkdir -p ~/.agents/skills ~/.claude/skills
cp -R r3xstack/skills/* ~/.agents/skills/   # Codex
cp -R r3xstack/skills/* ~/.claude/skills/   # Claude Code
```

On Windows (PowerShell):

```powershell
git clone https://github.com/r3xsean/r3xstack.git
New-Item -ItemType Directory -Force "$HOME\.agents\skills", "$HOME\.claude\skills" | Out-Null
Copy-Item -Recurse -Force r3xstack\skills\* "$HOME\.agents\skills\"
Copy-Item -Recurse -Force r3xstack\skills\* "$HOME\.claude\skills\"
```

To update, `git -C r3xstack pull` and copy again. Copying never deletes: when a skill is removed or renamed here, delete its old folder from your skills folders yourself.

## In more detail

### see-it-through

Normally you make two decisions, the approach and the result, and the agent handles the rest, apart from the questions its grill puts to you. A change that's already built starts at the result, and anything that changes what you approved comes back to you.

**Auto approve.** When your request says to auto approve, the ship message is your only approval. The agent answers its grill itself with each recommended answer, settles the same way anything else it would otherwise ask you before the ship message, and approves each explainer itself, revised ones included, by building the approach it recommends. It still sends you each explainer, marked auto-approved, and the ship message then also lists each answer and choice it made in your place. `kaizen` launches its runs this way, apart from direction items and any item you ask it to grill you on.

1. **The approach.** It first works out where the change should end up, asking, in its grill, only when that's unclear and the answer changes the work. For a bug, it first reproduces it on the base: a failing test and, when a user can see the bug, a capture of the running product. If it can't, it tells you before building a fix and marks what it says about the bug as read from the code, not tried; failure paths it couldn't reproduce become follow-ups rather than new guards. A check that finds nothing counts only once it has been seen to find the problem when it's there. For a feature, it writes down what you should see or be able to do.

   It then grounds the design in the code, following [design.md](skills/see-it-through/design.md): who owns the behaviour and its state, every caller and every writer of that state, and the contracts they rely on. When the change moves ownership or a boundary, it first finds out why things are shaped this way today. For a bug, once it reproduces, it decides whether the state behind it is legitimate: a legitimate state is handled where it enters the system, and whatever produces an illegitimate one is fixed. It also checks the destination for newer commits and open work on the same behaviour. Then it runs `grill-me` on the request with what it has reproduced and found, and your answers count as part of the request from then on, with the grill's assumptions going along, marked as the agent's. A design question it could answer by running something is settled with a throwaway experiment rather than by asking you. When even the smallest approach costs more than the problem, it recommends a smaller version or no change, and you decide. Every run also asks whether the existing structure fits, or whether removing or reshaping something would solve the change more directly than adding to it. When the change creates or moves ownership of state, adds a public API or a layer, makes a decision already made elsewhere, or works around an earlier workaround, the smallest patch and a structural option are weighed against each other in the back-and-forth, and the structural option doesn't win for looking cleaner.

   A medium or heavy run always argues the approach in a back-and-forth. A light run does so only when the change is one of those structural cases or the strong approaches differ materially; otherwise the agent writes the approach itself. When the run calls for a back-and-forth, the runner argues the approach with the other model, with a smaller version and no change among the options, and the agent's estimates of the change's reach and cost among the premises to check. The second look (`second-look`) then reads their record, with your request, and the reproduction when there is one, and says how it would make the approach better: a change to it, a different approach, a different reading of the problem, or that theirs is what it would do. What it raises goes word for word into the same back-and-forth, for up to 3 more exchanges; unless the debate adopts a point as given, the second look sees the new record once more, to concede the point or hold it.

   It sends you an explainer: the problem, why it happens, what changes (including the decisions the grill settled, with those you left to the agent marked, and the assumptions it stated, so that your approval covers them; and any decision that came up after the grill, with a recommendation a plain approval accepts), the approach, the alternatives weighed (including any point from the second look that wasn't adopted) and what a reviewer may ask. When the second look holds a point, the explainer is a choice instead: Approach A and Approach B, each written fully enough to build from, where they disagree, and the one your agent recommends; a plain approval builds the recommendation, and naming the other builds that. It builds nothing until you approve. Any reply other than an approval goes word for word into the same back-and-forth (in a light run with no back-and-forth, back to the agent) and comes back as a revised explainer.
2. **The result.** Before changing behaviour, it keeps the reproduction and every acceptance check it can write in advance as a baseline that runs again on the final candidate. Once built, it shows the reproduction passing, simplifies the diff, runs a code loop on it (the other model reviewing, the breaker on its own default) and, when a user can see or do what changed, captures it (for a bug, before and after through the same flow). Simplifying, as [simplify.md](skills/see-it-through/simplify.md) sets out, looks only at code the diff adds, changes, moves or leaves unused, never changes what the user sees, never touches the acceptance baseline, and uses the repo's own simplification skill when it has one; a test it deletes is named in the ship message. Then it sends a ship message: a recap, what changed since the explainer, the evidence, the captures, the write-up, the diff and the exact action it will take. When the code loop ended with unresolved disputes, a fresh agent on the second look's model reads which of them matter to what you get and what it would do next, and the message leads with them: each claim, what each side showed, that read, and what approving ships with them. The read is advice; the loop stays unapproved. Before sending the message, it checks the destination again for work overlapping the change. Saying "see it through" approves no push, PR or deploy; only your approval of the ship message does. A change you ask for instead is made and proved the same way, with a code loop when it changes behaviour, and comes back as a new ship message.

Along the way:

- **Light, medium or heavy.** Once it has reproduced the bug or written down the feature, it sets the run's tier, judging by the callers and state writers it found rather than by file names, and gives the tier with its reason in the explainer (in the ship message when there's no explainer). A run is heavy when a mistake would cost something that can't be taken back: existing data lost or corrupted, an irreversible action such as a delete, a payment, a send or a production write taken or taken in more cases, more access granted, something outside the repo broken that reads an API, file format or protocol the change alters, or ownership moved of state that other processes, users or stored data depend on. It's also heavy when, after tracing the callers, the agent still can't tell how the changed code is reached. It's medium when the change alters stored data, permissions, the ordering of concurrent operations, an irreversible effect, an outside contract or the ownership of shared state, but a mistake could be undone and stays inside the project; otherwise it's light. In a project with no users or stored data yet, a run is medium at most, and an upstream PR isn't by itself an outside contract. The tier sets the default models, and it only rises: when it rises before you approve the explainer, the approach is argued with the new tier's models, again if it already was; after, every later step uses them, and the ship message says the tier changed.
- **Structure before behaviour.** When a reshape can keep the current contract and makes the behaviour change easier to review, it lands first, with a check pinning the current behaviour, and the behaviour change goes on top. Internal callers of a replaced API move in the same change and the old API is deleted; a public API or an independently deployed consumer gets a migration plan in the explainer instead. A boundary later changes must respect is enforced with types, module exports or an import rule where the repo allows, and the reason for a non-obvious ownership decision is written in the repo's AGENTS.md.
- **The explainer stays true.** If a test, demo or review changes what you get, it sends a revised explainer and stops again. Smaller discoveries, such as using a different internal helper, go in the ship message instead.
- **Captures are made for a quick look.** Following [capture.md](skills/see-it-through/capture.md): when the result is a state, a paired before/after screenshot, with the recording of how a user gets there under it when an action leads to that state; a recording alone when the interaction itself is the result; the same data and framing before and after, setup kept off camera, and waits time-lapsed under a visible label. The agent looks at each capture before offering it, and a capture of the base or of a failed run never stands as a pass. A change with nothing to see gets no capture.
- **Public text is checked.** The PR, issue or release text follows the project's templates, with the captures where the template has room for them or under a heading of their own; on GitHub it attaches them when it publishes, unless the repo has its own tool for that. Before any public text that states a fact goes out, such as a PR description, a reply or a status update, a fresh fact-checker, on its own default model, checks every claim against the evidence, the captures and the diff. A claim the evidence doesn't back is cut. Before every push, it reruns the checks and redoes the captures that the changes since could affect.
- **After approval,** it carries the change to its destination. It builds on other people's pushes instead of overwriting them. Every review comment gets a fix or a one-line reason; one about a problem that also happens on the base is judged as `code-loop` judges a pre-existing finding, and a fix that changes behaviour gets its own code loop. A request that changes the scope or the approach goes back to the explainer; one that applies beyond this change comes to you with its link. When a fact proves posted text wrong, it corrects the text. When the change lands, closes or is replaced by someone else's version, it compares what reached the destination with what it last verified and reports what differs, without re-adding what others removed on purpose. For a deploy, it runs the verify flow against what's deployed.
- **Lessons.** When a problem gets past the code loop, or the loop finds a blocker or should, it logs the lesson in the repo's `.agents/lessons/log.md` (for a repo you don't own, in the folder that holds your process for it). Then it reads the log and lists follow-ups in its final message: for a lesson seen twice, a lint, type, test or verify check when a check could catch it, or a line in the repo's AGENTS.md when it needs judgement; for two lessons in one module, or two of one bug class, a structural question, naming the cause they share before any refactor is proposed. A refactor runs as its own see-it-through.
- **Changes already made.** If you say the change is already built, it skips the grill, the explainer and the back-and-forth. It writes the request from your words and what the change says of itself (commit messages, PR text), marking what it inferred, pins the base, finds the checks that fail on the base and pass on the change, writing one only for a promised behaviour none of them proves (for a change with no failure to show, such as a speed-up or a refactor, a check of what it promises), sets the tier the same way, and writes down the approach as built for the code loop. The ship message becomes your first approval, says that no explainer was approved, and carries any structural alternative and any finding that changes what you get.

### kaizen

It finds what's worth improving in a codebase, judges every finding, and, once you say "go", sees each one to do through from the thread you started it in. Nothing in it edits the code: every change is a `see-it-through` run.

You change any of its defaults by saying so when you start, in your own words; the rest stay as they are:

- **Scope:** the whole repo, or an area or path, "since the last pass", or "this branch", where the pass reads your branch's head and the files it changed, and the runs it launches start from that branch and land on it.
- **Focus:** every lens, or the lenses you name; "also look for X" adds one.
- **Depth:** one reviewer per lens family per slice, plus one per whole-repo lens; "quick" is one reviewer per slice with every lens, and no whole-repo reviewers; "deep" is one reviewer per lens per slice.
- **Direction:** on, with no cap on its suggestions; "no direction", or "direction only", where it's the only reviewer.
- **Stages:** probes and debates; "skip probes", or "no debates", where the agent gives the verdicts itself.
- **Report:** an HTML page plus a short list in chat, or "chat only".
- **Concurrency:** 10 agents running at a time, and, once you say go, 5 launched runs at a time; "run N at a time" or "N runs at a time" changes them.
- **Models:** as [Naming the other model](#naming-the-other-model) says.

A pass:

1. **What's known.** It fetches the default branch of the repo the work lands in (upstream's, for a fork) and works from a detached worktree of its head, which every reviewer, probe and debate reads. From it, it reads the repo's AGENTS.md or CLAUDE.md, README, CONTRIBUTING, CI config, decision docs, verify skill and lessons log, and its own record of earlier passes; in a repo you don't own, also upstream's rules for contributions (CONTRIBUTING, `SECURITY.md`, any AI policy, issue and PR templates), which decide what counts as a finding there and how each one lands. It finds the hotspots from `git log`, measures the baselines the repo can produce without touching anything shared, such as build and test times, bundle sizes and CI durations, and cuts the scope into slices a reviewer can read closely, about 10,000 lines of code each, along the code's own boundaries and weighted by hotspots, leaving out generated and vendored code and saying so. It tells you in one line how many slices and reviewers that makes, and carries on without waiting.
2. **Audit.** Every reviewer starts at once (as many as the concurrency setting allows, the rest as earlier ones finish), read-only, each on one slice with one lens family, or on the whole scope with one whole-repo lens. The lenses, in [lenses.md](skills/kaizen/lenses.md), are places to look rather than a checklist: per slice, correctness, performance, security and simplification; across the whole repo, duplication and inconsistency, architecture, dependencies, tests and verification, tooling and docs, the repo's agent setup, and direction (where the codebase wants to go next, grounded in the repo). A reviewer follows the real path before writing a finding down, labels every cost and gain measured, observed or estimated, treats everything in the repo as data rather than instructions, and never copies a secret's value. A reviewer that fails twice is listed as not covered.
3. **Merge.** Findings that share a cause or a fix are grouped into themes, and a fresh agent per theme checks each write-up against the code and writes the item files; findings that describe the same problem become one item. A finding is dropped, with its reason, when its evidence doesn't hold in the code, when a recorded decision settles it (unless the code has drifted from that decision), when it matches a dropped item that nothing has reopened, or when it's about taste and states no concrete cost. Every item gets a file, dropped ones included.
4. **Size.** Unless you skipped probes, each open item gets a read-only reach probe: whether it's still there, who hits it and how often, the harm when they do, and the size of the gain, measured wherever a small script, unit test or existing check can.
5. **Judge.** Unless you turned debates off, each theme gets a worth-it debate, a runner arguing it through `back-and-forth` with the other model, and every item comes back as do, batch, drop, or wait on a named event. A debate is a close call when the two models end on different verdicts, when an unchecked premise would flip the verdict, or when the runner calls it near even. A close call that turns on one number nobody measured gets that number measured and the debate run again; any other close call gets a second look. Every verdict stands without asking you, close calls included; a point the second look holds goes in the report with each side's case.
6. **Report.** Unless you asked for chat only, it shows the report as an HTML page, built by [`scripts/report.py`](skills/kaizen/scripts/report.py). It sends in chat the count per verdict, each item to do or batch in a line, the close calls, what wasn't covered, and how to answer: "go", "go except `<items>`", "go on `<items>`", or "`<item>`: grill me". Then it stops until you say go.
7. **Go.** From here the thread is the pass's orchestrator and reads no code itself. It launches each item to do, and each batch as one, as its own thread running `see-it-through` with auto approve, in a new worktree from the remote default branch, with the finding, its probe and its debate as leads to reassess rather than conclusions. In a repo you own, the destination is merged into the default branch, through a PR where the repo merges through PRs. A direction item launches without auto approve, so its product decisions come to you, and "`<item>`: grill me" launches that item without auto approve, so its grill and explainer come to you. When the repo has no verify skill, it first launches one `make-verifiable` run, set up for the flows the launched items touch, and launches the rest once that has landed. Items that cite the same files launch one after another, each once the one before has landed; the rest launch at once, up to the concurrency setting, with the next starting as each one finishes. Each run sends this thread a short form of its ship message (its recap, the exact action it will take, and links to the PR or diff and the captures), and you approve in either place: "ship all" or "ship `<items>`" here is passed to each run it covers in your exact words. Runs report back when they ship, drop or get blocked, and send improvements they find outside their scope as leads, each of which becomes a new item that is probed, judged and, on do, launched. Whenever a message arrives, it checks the event each waiting item waits on, such as a merge or a maintainer's reply. When nothing is running and nothing can launch, it writes a closing summary at the top of `STATUS.md` (what shipped, what was dropped, what still waits) and rebuilds the report.

In a repo you don't own, an item lands as a PR from your fork, unless upstream asks for an issue first or the item needs the maintainer's product call; then it drafts the issue, files it once you approve, and the item waits on the maintainer's reply. A security item goes the way upstream's `SECURITY.md` asks, never as a public issue or PR unless that file allows it. When you keep a process folder for a repo, the record goes there, and when that folder has its own rules for taking on and launching work, those rules win over sizing, judging, reporting and launching.

"Kaizen continue", in any thread, rebuilds the board from `STATUS.md` and the item files, checks each launched thread, sends each run still going that thread's link as where to report from now on, and carries on launching and shipping. An item judged before the code it cites changed gets a fresh probe and debate before it launches. A new pass in a repo with a record starts from the beginning: its reviewers get the items already on record for their slice, and a dropped item reopens only when what its verdict said would reopen it has happened, or the code it cites has changed. The briefs each stage fills in, and the item file format, are in [briefs.md](skills/kaizen/briefs.md).

### code-loop

The agent pins the base and runs the checks that cover the change, fixing any that fail. Then it starts fresh agents on the other model (the breaker on a model of its own when the calling skill names one, as `see-it-through` does):

- a **reviewer** that only reads and traces. It writes acceptance conditions before reading the diff, and how it would make the change itself; its own approach counts as a finding only where it meets a condition the diff fails, or meets every condition with less code. It checks the change against the repo's rule files and looks for structural problems: competing ownership of state, a decision made in two places, an obligation callers must remember, or a boundary callers can bypass. It grades each finding as blocker, should, nit or pre-existing.
- a **breaker** in its own worktree. It writes the smallest test for each condition and checks whether the change's own tests still pass with the guard they should catch undone. Tests that cover something no existing test does are kept as a patch, and the agent commits each one or names the existing test that covers its condition.

When the diff changes only comments, docs or formatting, there's no loop. When it changes no code that runs, there's no breaker. Otherwise both start together in round 1, except in a light run, where the breaker starts only after the reviewer replies, and only if a test could settle something the reviewer couldn't verify.

The agent grades every finding itself by the reviewer's definitions, whatever label it came with, and treats each condition the breaker broke, and each of the change's tests that still passes with its guard undone, as a finding. For an agreed finding, it reproduces it, preferably with a failing test, and applies the smallest fix to every instance of the same mistake that the change introduced or exposed, preferring to delete or narrow code over adding a lock, cache, helper or option. For a disputed one, it pushes back with evidence. "That can't happen", read from the code alone, leaves a finding disputed rather than dropped. It never agrees just to end the loop. A nit on code the diff adds, changes or moves is applied when its fix deletes code, reuses what the repo or platform already provides, or matches the repo's standards or the code around it; one whose fix would add a path, case, option or compatibility layer, change what the user sees or gets back, or that is only taste is declined in one line. After answering, it removes anything the review added outside tests that no accepted finding needs.

Each round starts fresh agents, and a timeout or error never counts as approval: the agent that failed is restarted once. A further round runs only while a blocker or should is open or behaviour code changed, and an approval from the reviewer ends the loop early. A condition the breaker couldn't test gets a fresh breaker when the cause can be fixed; one that needs an end-to-end run is listed for the author. If a blocker or should is still disputed after round 3, a fresh agent tries to reproduce it ([dispute-round.md](skills/code-loop/dispute-round.md)). A reproduced finding is fixed and a refuted one dropped. An inconclusive one leaves the loop finished with an unresolved dispute rather than approved. You're never asked to settle a dispute.

The final message reports the rounds run, the models, what the findings changed (each tagged behaviour, test, claim or polish), the diff size before and after, any finding dropped because a test or output showed it wrong, each declined nit or pre-existing finding with its reason, what the breaker tested and broke (and which of those the reviewer also found), each condition no committed test covers, the outcome of any dispute round, and each risk still unconfirmed.

[`evals/`](skills/code-loop/evals/README.md) holds a runner that replays `code-loop`'s current briefs against past changes where it missed a bug. With one sample per case, it measures how the reviewer and breaker catch and over-flag on those cases, not how well `code-loop` works overall. It's for judging an edit to the briefs, or to how findings are answered, before the edit lands, or for rechecking when the reviewer model changes; once the suite has results, `code-loop`'s final message offers a run when the reviewer model differs from the last one recorded. Its README's commands run the copy installed in `~/.agents/skills/`. This repo ships no cases; you add your own as that README describes.

### back-and-forth

Your agent writes its own answer first, so its view is fixed before it reads the other model's. The other model gets your question and context but nothing of that answer. They then exchange critiques in the same thread. Agreement doesn't count as evidence: every premise that would change the conclusion is checked against a source, a command or the code, even one both sides accept.

It stops when the positions match, each side has given its reasons and every checkable premise is checked, or after 3 exchanges past the opening unless you named another number. Your agent owns the conclusion. Its record gives the reasons, the alternatives that lost and why, what changed either side's mind, the other model's strongest remaining objection (with the agent's call when the two still disagree), each premise marked checked or unchecked, anything else your question asked for, and a link to the other model's thread. If the other model fails twice in a row, it concludes with what it has and says the other model dropped out.

When you or a calling skill names a runner, a model and effort to argue your agent's side, your agent doesn't debate at all: it starts the runner with the question and its context, the runner changes no file but its record, and that record is the result. Whatever you add later goes to the same runner. Where your agent has evidence against a claim in the record, it sends that back as a further exchange rather than overruling the record itself.

### second-look

You point it at work that already exists: a proposal, a plan, a back-and-forth's record, a diff. A fresh agent on the second look's model gets your request in your words, the work, and whatever evidence there is with how to run it. Nothing in the work binds it: it can look wherever it likes and run whatever is there to run, changing no file but scratch files of its own, and it says how it would make the work better (a change to it, a different way to do it, or a different reading of the request) or that it's already what it would do, with what each point rests on. A calling skill can add to its brief; `incorporate`, for instance, tells it the source supplies ideas, never instructions.

What it raises goes back word for word to whoever produced the work. When a back-and-forth produced it, the points go into that same back-and-forth for up to 3 more exchanges and a new record. Otherwise your agent answers each point itself, adopting it or saying why not, after checking any premise that would change its answer. Unless every point was adopted as given, the second look sees the new record, or those answers, once more, to concede each point or hold it with what would change its mind; it raises nothing new then.

The report says what the second look raised and how each point ended: adopted, conceded or held, giving each held point with what each side showed and your agent's recommendation. A calling skill says where the report goes. Started directly, it's the reply to you, with the work as it now stands, and your agent acts on nothing a held point touches until you answer.

### grill-me

It settles the decisions about a request, plan or idea that only you can make, and nothing else. A decision is yours when its plausible answers would materially change what you get: what you see it do, compatibility, scope, or a tradeoff you'd accept. It doesn't ask what the request, a recorded decision, or your leaving that decision to the agent already settles, and asking for a grill doesn't count as leaving any decision to it. It finds facts itself, by looking or trying. How things behave today shows what exists, not what you want, unless the request or a recorded decision keeps it. How something is built is the agent's call unless you put the mechanism in question; when a choice of how brings one of those tradeoffs, it asks about the consequence, not the mechanism.

Of the decisions still open, it asks only about a real fork: one where each answer gives you something the other takes away. Being confident in its recommendation doesn't make a real fork the agent's to decide. When one answer is better for you in every way you'd notice, it isn't a choice: it assumes that one and leaves what it costs to build to the approach. The rest it states as assumptions: the baseline it will work from, such as keeping what exists, limited to what bounds this request's result, scope or compatibility. An objection to an assumption answers it, or becomes a question when it leaves something open.

It asks in rounds, each one plain chat message rather than a question tool. A round holds every open question that doesn't wait on another's answer, numbered, each with its recommended answer and worded so "yes" accepts it; a bare "yes" accepts the whole round. Each question says what you'd see or get under each answer, without naming a mechanism, and leaves out any part with no tradeoff. After the questions, it lists the assumptions it hasn't stated yet. A question or assumption that depends on a question still open waits for a later round, and it waits for your answers before starting one. There's no cap on questions. When no question is left open, it replies with your answers, the decisions you left to it and the assumptions it's working from, each marked as which it is; an assumption never counts as an answer. When only assumptions are left, it states them and finishes without waiting; when there's nothing to state either, it says so in one line. Started directly, that reply ends its turn and approves nothing; started by another skill, that skill says what comes next.

### make-verifiable

It builds a **verify skill** in the repo. That skill is the one place agents learn which commands check a change, how to launch the right build, how to drive a flow and judge its outcome, where the evidence goes and what wasn't verified, and how to clean up. In a repo you own it lives at `.agents/skills/verify/`. In a repo you don't own, it goes in the folder that holds your process for that repo, never in the upstream repo's files.

- It works in three modes: set up, extend, or repair. It covers only the flows you name.
- Every check CI runs maps to a local command or is marked CI-only. It adds an ordering check, which runs the real code through every order of replies and events up to a bound, only when the request or a lesson names state that several operations change across awaits. A failing order counts as a bug only once a plain test on the real code reproduces it.
- Its helpers pass the repo's lint and format and stay out of the repo's own test run, so adding them doesn't change what the repo's checks run.
- Flow helpers start what the flow needs, such as a local database, when that can be done locally and safely, and launch the product as close to how users reach it as the environment allows. They drive it with throwaway data, assert what the user sees and what was saved, and save evidence, including a screenshot or recording when the outcome is visible. They clean up only what the run created.
- A missing prerequisite or unsupported flow reports INCOMPLETE, never a pass. A capture the flow can't make is reported INCOMPLETE on its own, and the flow's verdict stays as its checks found it. Each new assertion is seen to fail on a broken outcome before it's trusted.
- When a verify step fails, it decides whether the cause is the environment, drift in the verify skill, or a product regression. It fixes only the drift and reports a regression as a bug.
- Recording helpers follow [recording.md](skills/make-verifiable/recording.md): the raw recording is kept, the clip is trimmed to its start and end marks, and waits are time-lapsed by default, at most about 8×; a wait still long at that rate becomes a cut with a card. Each clip comes with a pacing report, a contact sheet and key frames for reviewing it.
- It commits only when you, or the skill that called it, say so. Its report says what it added or changed, the failures each new assertion and wrapper was seen to catch, and what's still INCOMPLETE.

### design-process

You decide direction and taste. Models judge execution: whether the task can be done, whether the numbers are true, whether anything breaks, hides or misleads. A score or a council never chooses between directions or overrules a decision you recorded. If the project has its own design skill, the agent follows that skill, which may send it back here for a phase.

It keeps its files in `docs/design/` unless the project's AGENTS.md names another place. They are a product brief, a `DESIGN.md` of your decisions and reactions, a `harness.md` describing how screens are run and captured, and a `run.md` per run. Templates are in [`templates/`](skills/design-process/templates/).

- **New UI:** bootstrap → explore → you pick → refine → council → you approve a reference → holdout → ship.
- **Existing UI:** bootstrap → council → approve → ship, with refine first when you want visible changes. A narrow tweak starts at refine.

A run enters at the phase you ask for, but bootstraps first whenever the product brief, `DESIGN.md` or `harness.md` is missing. The phases:

- **Bootstrap** reads the project first, then asks you, in one message, for what's still missing, with a second round only when an answer opens a new gap that would change a design decision. It builds the parts of a capture harness the run needs, on fixture data from the real product, reusing what the project already has.
- **Explore** has three designers each build a different direction, blind to the current UI and to each other. Each checks its plan against the defaults AI-made UI tends to fall into and revises any it can't justify for this product. While they build, the agent checks that the fixtures and any numbers derived from the product's logic are correct. The directions are shown to you under random letters, with stances, notes and scores held back until you've reacted, and you pick, or ask for another round.
- **Refine** responds to your reactions. It makes a local change directly, shows 3–6 variants on the real screen when you're unsure, and makes a structural change within your decisions and the craft floor, reviewing it with `code-loop` when it changes code beyond styling and you've named a model.
- **Council** runs scored rounds on fresh screenshots, compared with one or two competitor apps. Each member works read-only from a pack of the captures, the product brief, the craft floor and your decisions, without member names or earlier scores. It suggests members from different providers and never substitutes one that's unavailable. The default target is every member scoring every screen at least 9 and above every competitor, unless you set another. It acts on a finding when more than one member raised it, or when one member raised it at high or medium severity and the agent confirmed it in the captures. Execution problems get fixed. Findings that contradict your decisions are skipped. Changes with a real tradeoff are held for you. It reports after each batch of five rounds, or sooner if the target is met, and runs another batch only on your yes. When the work ends in a pull request, the score table goes in its description.
- **Holdout** comes after your first approved reference. A fresh agent designs a surface not yet designed from the skill, the project's files and the harness alone, and lists every guess it had to make. Each guess is fixed in the file that should have answered it, or recorded as open.

Only your words approve a reference screen; scores never stand in. Every reaction you give goes into `DESIGN.md` in your exact words, as a like, a dislike or a defect. Its scope is never widened, and it becomes a general decision only when you state it generally or say yes. When a reaction contradicts a recorded decision, it asks you which wins. Every screen is checked against a [craft floor](skills/design-process/references/craft.md). Captures use fixture, seed or demo data, never your own account or real people's records, and nothing showing personal data or adult content goes into a council pack, a reference capture or a commit. Other design skills can do bounded jobs inside a phase, as [integrations.md](skills/design-process/references/integrations.md) lists, but none is required, and none writes `DESIGN.md` or chooses between directions.

### incorporate

The agent reads the source: a post as given, with its images or your description of them; an article, which it fetches; or a video, which it reads through `watch-video`. It reads an X link in a background T3 Code browser tab, read-only: the post, its thread and the replies on that page, and its images. It researches the wider discussion beyond that, such as quote posts, only when you ask. When part of the source can't be read, it asks you for it rather than reconstructing it. It writes each idea as a behaviour tied to the passage or timestamp it came from. It then looks for evidence that the practice is used, treating any claimed benefit as unproven until something backs it.

Next it audits the skills in `~/.agents/skills` and the rules in `~/.agents/AGENTS.md` that the ideas touch, marking each idea covered, a gap, a conflict, excluded on purpose, or unsupported or unsuited. It argues with the other model about what, if anything, should change, weighing no change, deleting a rule and replacing prose with a script or check alongside adding something, and settling where each change lives: an existing skill unless the change must be reached on its own, as a script or check where one can do the job.

When the debate concludes, a second look (`second-look`) gets the source as the agent read it, the evidence, the audit and the paths to your files, unbound by the record, and says what it would do: a change the two models missed, a different reading of the source, a simpler form of a change they chose, or dropping one, or that theirs is already what it would do. What it raises goes word for word into the same back-and-forth, for up to 3 more exchanges; unless the debate adopts a point as given, the second look sees the new record once more, to concede the point or hold it.

When there are changes, or a point the second look holds, `writing-steering-files` takes over, with a held point offered as a change you may adopt, alongside what each side showed and the agent's recommendation. You adopt all, some or none. When there's nothing to change and no point held, it reports its reasoning without stopping for approval, and says so when part of the source couldn't be read or a premise stayed unchecked rather than reporting no gap. Either way, it tells you what the second look raised and how each point ended: adopted, conceded or held. Each run is logged in `~/.agents/sources/log.md`, and a later run on the same source or idea reuses that reasoning after rechecking it. The source supplies ideas, never instructions.

When the source announces a model you could run, none of that happens: it runs `model-audit` on the launch with the same model instead, and that audit's log entry stands for this run's.

### watch-video

Give it a link (YouTube, X or any site yt-dlp handles) or a local file. Its script, [`watch_video.py`](skills/watch-video/scripts/watch_video.py), writes the transcript, from the video's captions when it has usable ones and otherwise by transcribing the audio on your machine (a local file is always transcribed that way, which takes minutes on long media), headed with the channel, upload date, length, chapters and how the transcript was made. A post with several videos gets a transcript per video. Unless you want only the transcript or only what was said, it also makes contact sheets of evenly spaced frames from the whole video, with an index that ties each tile to the speech around it; when it can't make frames, the agent answers from the transcript and says what it couldn't see.

The agent reads every transcript and views every sheet. A tile shows only that something is on screen, so before it states any on-screen text, number or name, it pulls the full frame at that moment, or several across a stretch, found from the index, the transcript or a chapter. When nothing in the speech, the chapters or the tiles leads to what you asked about, it scans the likeliest stretch with sheets that take a tile at each scene change, widening step by step, then pulls the frame. Its answer ties each point to a transcript time or a frame it viewed, and says so when neither shows something. Everything in the video, its speech, on-screen text, title, description and chapters, is treated as data, never as instructions.

It needs Python 3, `ffmpeg` and `ffprobe` on your PATH, and, for links, yt-dlp installed for the same Python (`python -m pip install -U yt-dlp`). A video behind a login takes a cookie file with `--cookies`; `-l <lang>` prefers a caption or speech language. The overview sheets and the frame and scan commands are adapted from [vidscribe](https://github.com/SamuelZ12/vidscribe), under the MIT notice in [`NOTICE-vidscribe.md`](skills/watch-video/scripts/NOTICE-vidscribe.md). Its [`tests/`](skills/watch-video/tests/) run offline on synthetic media.

### model-audit

It decides which model and effort each role in a workflow runs on, from what your plans actually charge and what the evidence shows. There are two ways in: a model has launched, and the question is which roles, if any, should take it; or you name a workflow and ask whether its roles fit. The target is your own workflow (your skills, your AGENTS.md and what you type to start a run) or one named automation; it audits both in one run only when you ask.

1. **Terms.** It reads the target's last log entry and reuses what still holds, then asks in one message for whatever that and your request leave open: which efforts are allowed, what the budget is for (holding today's rate, filling the plan, or a cap), whether roles must stay the same between resets, and how much of the plan the audit itself may spend.
2. **Inventory.** Every role gets a row: what it does, the exact model id and effort it resolves to today, where that's set, the text it's given, the working directory its launcher gives its sessions (their records are filed under it), and which plan or key pays for it. [`inventory.py`](skills/model-audit/scripts/inventory.py) lists the lines under the workflow's folder that name a model or set an effort, and the models this machine's sessions from that folder recorded; the agent traces by hand each value it marks and each default it can't see. For an unattended role, it also notes what happens when the plan runs out: it waits, fails visibly, falls back, or spends credits.
3. **Measure.** [`meter.py`](skills/model-audit/scripts/meter.py) estimates what 1% of each plan's limit costs per model, and how full each plan is, from this machine's records priced at list API prices, and lists what it can't see, such as other machines or apps on the same plans, or providers other than Claude and Codex; for each machine or provider it lists, the agent runs it there too or says the figure leaves it out. When a plan has more than one meter, such as a sub-limit that counts only some models, the agent names the meter each role draws on, and it gives the target's share of each plan from the session records. A recipe is never priced on API prices alone: when a rate that could reverse the choice has no clean measurement, the agent runs one real task on that model at that effort with nothing else running and measures again, or marks every recipe that leans on it provisional.
4. **Evidence.** For a launch, it reads the launch post, the capability and behaviour sections of the system card, and the vendor's prompting and migration guides in full, taking scores at the efforts you'd run, not the one the vendor leads with. For a workflow, it reads the recorded runs with their outcomes, retries and failures. For both, it looks for independent results, saying what each measures and who ran it, and weighs results that are hard to tune for above the rest. When two models score alike, it expects the bigger one to do better in practice.
5. **Recipes.** It presents a few, with no change and any that go over a limit among them. Each gives every role its model and effort and its expected use of every plan it draws on, with each estimate marked measured or guessed; for an automation, retries and failed runs count in the cost of a successful result. You pick.
6. **Scope.** Only what the changed roles touch is in scope: their text, the handoffs into and out of them, and instructions they share, checked against the roles that didn't change. A launch is no reason to clean up anything else. A line goes only when it covered a weakness of the model that left the role, repeats another line, describes mechanics that no longer exist, or conflicts with something it can show; a line with no recorded reason otherwise stays.
7. **Test.** It runs the smallest tests that could change the choice: a role's regression suite when it has one, and for an automation, recorded inputs replayed on the candidate with publishing and writes off, compared on outcome and cost per successful result.
8. **Debate.** It goes back and forth with the other model on the picked recipe and the changes it needs, with the inventory, the measurements and the evidence as context.
9. **Change.** Each change goes through the route its file has: a steering file through `writing-steering-files`, code and configuration through `see-it-through` in that repo. What an unattended role does when the plan runs out is set in its configuration, never in its prompt. When it audits your own workflow, automations that pin an affected model are listed as follow-ups, not changed.
10. **Log.** It appends a dated entry with the target, each role's model, effort and exact id, where each is set and at which revision, the measured rates and how they were measured, why the recipe won and what lost, what's approved but not yet made, and what's still unmeasured.

The scripts need Python 3. [`tests/test_scripts.py`](skills/model-audit/tests/test_scripts.py) runs each of them against records in a throwaway home folder.

### writing-steering-files

It covers eight branches: create or edit a skill, an AGENTS.md, an automation prompt (one that runs unattended) or a product prompt (the system prompt behind a feature other people use). Every branch runs the same loop; an edit grills and shapes only the change, not the whole file:

1. **Scope:** the file and the behaviour change. For an edit, "currently the agent does X; after this it should do Y." When the edit answers something an agent got wrong, it first names what produced it, often a line in the file itself, asking the session that misbehaved why when it's still reachable. The fix then goes in this order: rewrite or delete the line that caused it, move the rule into a tool or script that makes it unnecessary, and only then add a rule.
2. **Grill:** every rule becomes "given X, the agent does Y" and is tested for ambiguity, no-op, overreach and whether it belongs elsewhere. The decisions only you can make, the forks rather than the list of rules, go through `grill-me`.
3. **Shape:** the structure, one line per section, before any text is written.
4. **Draft.**
5. **Probe:** only the runs you approved, and none when you approved none. These can be probes against the real feature for a product prompt; a skill's regression suite, when the skill has one and the edit touches what it tests; a replay of the failure an edit answers, when the original prompt and context are still available; or, for a skill, an AGENTS.md or an automation prompt, a cold run by a fresh agent that reports where it had to guess.
6. **Walkthrough:** headed with each changed file's size against the round's base (the files before the first edit, then as the last walkthrough left them): words before and after, lines added and removed, and a flag when the edit only adds. Then what each section encodes, every judgement call made while drafting and each sentence removed, and then the real text: a link to each changed file, with every sentence added or rewritten since the base quoted word for word under its section. It never pastes a whole file or a diff into chat; for a file that's new since the base, the link carries the text. For an edit, it covers only the changed sections.

You approve the scope, the intents and the shape before any text exists, in one message when none of them waits on your answer to another, then the real wording. Edits leave approved behaviour alone; when the change conflicts with something already in the file, it shows you the conflict and proposes replacing or removing the old rule. Each kind of file has its own craft file, which the agent reads before the grill: [skill-craft.md](skills/writing-steering-files/skill-craft.md), [agents-md-craft.md](skills/writing-steering-files/agents-md-craft.md), [automation-prompt-craft.md](skills/writing-steering-files/automation-prompt-craft.md) and [product-prompt-craft.md](skills/writing-steering-files/product-prompt-craft.md). The skill craft file, for instance, covers whether a skill should fire on its own, only on a phrase you say, or only when you type its name.

## How this repo works

It's published automatically from my private skills source: a job checks every five minutes and, when the skills have changed, publishes them as one commit. Changes go into the private source first, so open an issue rather than a pull request.
